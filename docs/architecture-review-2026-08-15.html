Candidate 01

One evidence journey, two Renderer Integration adapters

Strong in-process
fixtures/consumers/controller-action-journey.mjs · fixtures/consumers/react-renderer-harness.mjs
fixtures/consumers/journey-evidence.mjs · tests/release-evidence-{contract,instrumentation}.test.mjs
Problem
Semantic and Scene Event Shield journeys are encoded twice; scenario rules, timing, observations, and Renderer Integration mechanics are interleaved across 1,875 lines.
Solution
Concentrate sequencing, Wrist Menu Events, recovery rules, and coverage assembly in one deep module; keep Three and React as the two adapters at a real seam.
Deletion test
Delete either matrix and its scenario complexity reappears in the other adapter. The behavior earns one shared module.

Benefits

  • locality: cases change once
  • leverage: one matrix, four lanes
  • two adapters justify seam
  • tests hit one interface
ADR-0001: instrumentation changes invalidate affected automated Evidence Records.

Candidate 02

Make the presentation seam the test surface

Strong in-process
src/three/{presentation,wrist-menu-presentation,presentation-atlas,reach-layout}.ts
tests/{reach-scroll-three,theming-presentation-three,atlas-presentation-three}.test.mjs
Problem
Lower-level mutators exist mainly for tests, while targetability lives in both the managed and default implementations. Tests can pass past the seam while production behavior disagrees.
Solution
Keep pooling, atlas rebinding, scrolling, and targetability inside the default Presentation adapter; test it through the existing presentation seam used by custom adapters.
Deletion test
Delete the lower-level mutators and only tests break; the production behavior remains behind the existing factory. Those surfaces are shallow.

Benefits

  • locality: hit policy lives once
  • leverage: one observable interface
  • pool changes stay internal
  • tests survive implementation changes
ADR-0001: Presentation and instrumentation changes refresh Evidence Freshness.

Candidate 03

Candidate 04
